# ADR-001: 规则参数化——RuleSet 经 transition 逐调用传入

日期：2026-09-22
状态：已采纳

## 背景

规则引擎最初把桌规（软 17 停牌、天然 3:2 等）硬编码在 `transition` 内。为了在不污染默认行为的前提下支持常见规则变体（以及让测试能确定性覆盖变体分支），需要一种规则注入方式。约束：领域层必须保持纯函数、无全局可变状态；默认 `RULES` 行为一字不能变。

## 决策

- 新增声明式 `RuleSet` 接口；`transition` 增加第 4 个参数 `rules: RuleSet = RULES`。
- **仅接线** `standSoft17`（软 17 停牌/补牌）与 `blackjackPayout`（`[3,2]` / `[6,5]`）两个字段；其余字段（`decks`、`split`、`insurance`、`surrender`、`version`）以字面量类型钉死为当前唯一实现值。
- 规则对象**逐调用传入**，引擎不保存规则状态；调用方（useGame）始终使用默认 `RULES`。

## 理由

- 逐调用传参保持引擎纯函数本质：同一进程内可并存不同规则的对局/测试，无全局切换风险。
- 替代方案「模块级可变配置」或「构造引擎实例」都被否决：前者引入隐式全局状态（导入存档、测试并行时易串扰），后者为一个纯函数模块增加无谓的生命周期。
- 只接线两个字段是刻意的：钉死的字段让"哪些规则其实没实现"在类型层面可见——改动钉死字段 = 实现该规则 + 升 `rulesVersion` + 更新 `contracts/save-format.md`，无法在 UI 上误开。

## 后果

- 正面：变体可测试（已含 6:5 赔率、软 17 补牌用例）；未来规则扩展路径明确。
- 代价：调用方多一个参数；`blackjackPayout` 结算为整数运算 `bet + bet×p/q`，赔付语义固定为净赔，新比例需保证整除合理性（下注为 100 的倍数，3:2 与 6:5 均产出整数）。
- 后续工作：软 17 变体测试补全登记为 REQ-2026-002。
